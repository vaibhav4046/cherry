### Site tools help article (ChatGPT desktop app)
- "Site tools" are tools a website provides (via WebMCP, described as a proposed web standard) that ChatGPT can use directly on a page open in the ChatGPT desktop app's built-in browser; they exist only when the account has access and the website provides them. [VERIFIED — "Using site tools in the ChatGPT desktop app | OpenAI Help Center", https://help.openai.com/en/articles/20001423-using-site-tools-in-the-chatgpt-desktop-app, accessed 2026-09-02]
- Scope: site tools operate on the webpage you have open, its current state and your signed-in session; ChatGPT can work across tabs, but each tool is available only on the page that provides it and does not carry over to another page or website. [VERIFIED — "Using site tools in the ChatGPT desktop app | OpenAI Help Center", https://help.openai.com/en/articles/20001423-using-site-tools-in-the-chatgpt-desktop-app, accessed 2026-09-02]
- Persistence: "Site tools are available only while the relevant webpage is open." You must reopen the page to use its tools again. [VERIFIED — "Using site tools in the ChatGPT desktop app | OpenAI Help Center", https://help.openai.com/en/articles/20001423-using-site-tools-in-the-chatgpt-desktop-app, accessed 2026-09-02]
- Platform: currently only in the ChatGPT desktop app's built-in browser, not in Chrome; no separate connection or configuration is needed; can be disabled under Browser settings > Permissions > Enable site tools. Tools provided only by embedded content (iframes) are not currently supported. Availability also depends on the selected model. [VERIFIED — "Using site tools in the ChatGPT desktop app | OpenAI Help Center", https://help.openai.com/en/articles/20001423-using-site-tools-in-the-chatgpt-desktop-app, accessed 2026-09-02]
- UI: an arrow in the address bar (gray = available, blue = in use) lists the tools, shows whether each can read or make changes, and has a recently-used view; the conversation's Sources panel records which tools were used, per website. The built-in browser keeps its own browser state (separate sign-in from Chrome). [VERIFIED — "Using site tools in the ChatGPT desktop app | OpenAI Help Center", https://help.openai.com/en/articles/20001423-using-site-tools-in-the-chatgpt-desktop-app, accessed 2026-09-02]
- Security guidance: site tools may expose functionality not otherwise on the page, with named risks of data exfiltration and prompt injection; ChatGPT asks permission before interacting with a website; confirmation is required before sensitive actions (sharing personal info, purchases, deleting data, changing account permissions, sending messages); instructions from a website or site tool cannot authorize sharing or sensitive actions; if a tool requests information from outside the current page, ChatGPT asks the user to verify; an extra pre-call review of each tool and the data it would receive is performed; passwords go on the website, never in chat; vulnerabilities go to the Security or Safety Bug Bounty. [VERIFIED — "Using site tools in the ChatGPT desktop app | OpenAI Help Center", https://help.openai.com/en/articles/20001423-using-site-tools-in-the-chatgpt-desktop-app, accessed 2026-09-02]

### WebMCP spec (Draft Community Group Report)
- Status line: Draft Community Group Report dated 26 August 2026, published by the Web Machine Learning Community Group. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Entry point: a `modelContext` attribute on `Document` (SecureContext, SameObject) of type `ModelContext`, which extends `EventTarget`. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- `ModelContext` members are exactly: `registerTool(tool, options)` returning a promise; `getTools(options)` returning a promise of `RegisteredTool` records; `executeTool(tool, inputObject, options)` returning a promise of a string; and an `ontoolchange` event handler. There is NO `unregisterTool`, `provideContext`, `clearContext`, `listTools` or `callTool` in the IDL. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Tool descriptor (`ModelContextTool`): required `name`, `description` and `execute` callback; optional `title`, `inputSchema` (JSON Schema object) and `annotations` (`readOnlyHint`, `untrustedContentHint`, both default false). [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Unregister/abort contract: `registerTool` options accept an `AbortSignal`; when it aborts, the tool is unregistered. `executeTool` options accept an `AbortSignal` to cancel a running execution, and the tool's `execute` callback receives an options object carrying an `AbortSignal` so the implementation can stop work. Registering a name that already exists rejects with an `InvalidStateError` DOMException. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Cross-origin exposure: `registerTool` options `exposedTo` (list of origins) and `getTools` option `fromOrigins`; a `RegisteredTool` carries the registering `window` and `origin`. Access is gated by a permissions-policy feature named `tools` whose default allowlist is `self`; cross-origin iframes need `allow="tools"`. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Lifetime: tools live in a per-Document tool map; a new ModelContext exists per Document, so tools do not persist across navigation; unloading a document removes its pending executions and its map. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Stated limits: tool name length must be "between 1 and 128, inclusive." and restricted to ASCII alphanumerics, `_`, `-`, `.`; no numeric limit on description length or on number of tools is stated (a mitigation section discusses capping input lengths without prescribing values). [VERIFIED for name limit / UNVERIFIED for description-size and tool-count limits — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Security & privacy section enumerates: prompt injection via tool metadata (tool poisoning), via tool output, and via tools as attack targets; misrepresentation of intent (declared vs actual behaviour); privacy leakage through over-parameterised input schemas; same-origin boundary violations; private-browsing interaction. Mitigations: restrict maximum input lengths, shared attack-eval datasets, mark outputs with `untrustedContentHint`, and convey origin information to the model. No user-consent flow is mandated; that is left to implementations. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]
- Declarative (form-based) API: the spec section is explicitly a TODO and defers to the Declarative API explainer in the repo. [VERIFIED — "WebMCP", https://webmachinelearning.github.io/webmcp/, accessed 2026-09-02]

### WebMCP repo (webmachinelearning/webmcp)
- README defines WebMCP as a client-side API to expose web-app functionality as tools with natural-language descriptions and structured schemas for agents; examples use `document.modelContext.registerTool(...)`, `getTools()`, `executeTool(...)` and a `toolchange` event listener. [VERIFIED — "GitHub - webmachinelearning/webmcp: 🤖 WebMCP", https://github.com/webmachinelearning/webmcp, accessed 2026-09-02]
- Headless use is a stated non-goal: the API is "primarily designed for local browser workflows with a human in the loop". An open question in the README is how to handle tool responses when a tool causes navigation to another document. [VERIFIED — "GitHub - webmachinelearning/webmcp: 🤖 WebMCP", https://github.com/webmachinelearning/webmcp, accessed 2026-09-02]
- A declarative counterpart that synthesises tools from `<form>` elements is described in a separate `declarative-api-explainer.md`; the README itself shows no form attribute names. Other referenced files: `implementation-status.md`, `security-privacy-questionnaire.md`, `docs/service-workers.md`. [VERIFIED — "GitHub - webmachinelearning/webmcp: 🤖 WebMCP", https://github.com/webmachinelearning/webmcp, accessed 2026-09-02]
- Implementation status: "An Origin Trial is live in Chrome 149" with an early preview program; an origin trial is live in Edge 150; Firefox and WebKit standards-position issues are open; Brave has experimental support in Leo; ChatGPT Desktop is listed as supporting WebMCP. No dates or flag names are given. [VERIFIED — "Implementation Status", https://github.com/webmachinelearning/webmcp/blob/main/implementation-status.md, accessed 2026-09-02]

### Plugins in ChatGPT and Codex (help center)

[VERIFIED — "Plugins in ChatGPT and Codex | OpenAI Help Center", https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex, accessed 2026-09-02]

Some plugins work in both, others are Codex-only or workspace-limited; local/Codex-created plugins may need admin import before others can use them. [VERIFIED — "Plugins in ChatGPT and Codex | OpenAI Help Center", https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex, accessed 2026-09-02]

[VERIFIED — "Plugins in ChatGPT and Codex | OpenAI Help Center", https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex, accessed 2026-09-02]

Personal Skills are generally available to Business, Enterprise, Healthcare and Edu. ### Harness / App Server engineering post, Feb 4 2026
- The App Server is the bidirectional JSON-RPC API that every Codex surface (web, CLI, IDE extension, desktop app) uses to drive the shared harness (Codex core). Footnote: it is a JSON-RPC-lite variant that omits the `"jsonrpc":"2.0"` header and is "framed as JSONL over stdio rather than strict JSON‑RPC 2.0". [VERIFIED — "Unlocking the Codex harness: how we built the App Server | OpenAI", https://openai.com/index/unlocking-the-codex-harness/, accessed 2026-09-02]
- Protocol shape: client sends one `initialize` request first; primitives are Thread (durable, resumable, forkable, archivable), Turn (one unit of work) and Item (typed, with `item/started`, optional `item/*/delta`, `item/completed`); the server sends approval requests as server-initiated requests that pause the turn until the client answers. [VERIFIED — "Unlocking the Codex harness: how we built the App Server | OpenAI", https://openai.com/index/unlocking-the-codex-harness/, accessed 2026-09-02]
- Schema generation: `codex app-server generate-ts` (TypeScript definitions from the Rust protocol) and `codex app-server generate-json-schema` (JSON Schema bundle for other languages); clients exist in Go, Python, TypeScript, Swift and Kotlin; a test client is `codex debug app-server send-message-v2`. [VERIFIED — "Unlocking the Codex harness: how we built the App Server | OpenAI", https://openai.com/index/unlocking-the-codex-harness/, accessed 2026-09-02]
- Alternatives named: `codex mcp-server` (stdio MCP; limited to what MCP exposes), `codex exec` (scriptable CLI for CI), the Codex SDK (TypeScript, smaller surface at the time); the App Server is the recommended first-class integration. [VERIFIED — "Unlocking the Codex harness: how we built the App Server | OpenAI", https://openai.com/index/unlocking-the-codex-harness/, accessed 2026-09-02]

## E. Model Context Protocol specification (latest = revision 2026-07-28)

- "latest" resolves to revision 2026-07-28 (schema at `schema/2026-07-28/schema.ts`); the spec landing page lists base protocol, server features (resources, prompts, tools), client feature elicitation, utilities (progress, cancellation), opt-in extensions (Tasks, Skills over MCP, MCP Apps) and trust principles requiring explicit user consent before invoking any tool and treating tool annotations as untrusted unless from a trusted server. [VERIFIED — "Specification", https://modelcontextprotocol.io/specification/latest, accessed 2026-09-02]
- Statelessness: MCP is described as a stateless protocol; servers MUST NOT rely on prior requests on the same connection for capabilities, version or identity; every request carries `_meta` keys `io.modelcontextprotocol/protocolVersion` (required), `io.modelcontextprotocol/clientCapabilities` (required), `io.modelcontextprotocol/clientInfo` (SHOULD), `io.modelcontextprotocol/logLevel` (optional); servers SHOULD return `io.modelcontextprotocol/serverInfo` in result `_meta`; missing required fields are rejected with `-32602` (HTTP 400); every result carries `resultType` (`complete` or `input_required`); reserved error codes `-32020` HeaderMismatch, `-32021` MissingRequiredClientCapability, `-32022` UnsupportedProtocolVersion; JSON Schema 2020-12 is the default dialect and network `$ref`s MUST NOT be auto-dereferenced. [VERIFIED — "Overview", https://modelcontextprotocol.io/specification/2026-07-28/basic/index, accessed 2026-09-02]
- Capability negotiation: no `initialize` handshake; clients attach capabilities to each request; servers advertise theirs via `server/discover`, which servers MUST implement and clients MAY call (returns `supportedVersions`, `capabilities`, `instructions`, serverInfo, `ttlMs`, `cacheScope`); version mismatch returns `UnsupportedProtocolVersionError` listing supported versions; extensions are negotiated via an `extensions` map in capabilities. [VERIFIED — "Discovery", https://modelcontextprotocol.io/specification/2026-07-28/server/discover, and "Versioning and Compatibility", https://modelcontextprotocol.io/specification/latest/basic/lifecycle, accessed 2026-09-02]
- Architecture: host/client/server roles; each client talks to exactly one server and attaches version and capabilities to every request; servers cannot see the whole conversation; server-to-client needs (sampling, elicitation, roots) are returned inside an `InputRequiredResult` (multi round-trip requests), not as server-initiated requests. [VERIFIED — "Architecture", https://modelcontextprotocol.io/specification/2026-07-28/architecture, accessed 2026-09-02]
- Changelog vs 2025-11-25: sessions and `Mcp-Session-Id` removed; `initialize`/`initialized` removed; `server/discover` added; HTTP GET stream and `resources/subscribe` replaced by `subscriptions/listen`; `ping`, `logging/setLevel`, `notifications/roots/list_changed` removed; tasks moved to an extension; MRTR pattern and `resultType` added; SSE resumability (`Last-Event-ID`) removed; `Mcp-Method`/`Mcp-Name` headers and `x-mcp-header` added; `ttlMs`/`cacheScope` required on list/read results; resource-not-found now `-32602`; `iss` validation (RFC 9207) added; Roots, Sampling, Logging and HTTP+SSE deprecated; Dynamic Client Registration deprecated in favour of Client ID Metadata Documents. [VERIFIED — "Key Changes", https://modelcontextprotocol.io/specification/2026-07-28/changelog, accessed 2026-09-02]
- Transports overview: a transport is a binding; standard bindings are stdio and Streamable HTTP; custom transports MAY exist but MUST keep JSON-RPC format, message patterns and per-request metadata, and stream-based custom transports SHOULD reuse stdio framing; messages MUST be UTF-8; servers do not initiate JSON-RPC requests and clients do not send responses. [VERIFIED — "Overview", https://modelcontextprotocol.io/specification/latest/basic/transports, accessed 2026-09-02]
- stdio: client launches the server as a subprocess; one JSON-RPC message per line; "Messages are delimited by newlines, and MUST NOT contain embedded newlines."; server MUST NOT write non-MCP data to stdout and MAY log to stderr; server MUST NOT write JSON-RPC requests to stdout; cancellation is `notifications/cancelled`; shutdown = close stdin, wait, then escalate SIGTERM→SIGKILL (TerminateProcess/Job Objects on Windows); clients SHOULD restart a crashed server and retry lost requests; dual-era clients SHOULD probe with `server/discover` and fall back to `initialize` on any non-modern error. [VERIFIED — "stdio", https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio, accessed 2026-09-02]
- Streamable HTTP: single MCP endpoint accepting POST; each request/notification is its own POST with `Accept: application/json, text/event-stream`; response is a JSON object or a request-scoped SSE stream; notifications get `202 Accepted`; required headers `MCP-Protocol-Version` (must match `_meta`), `Mcp-Method`, `Mcp-Name` (for tools/call, resources/read, prompts/get), optional `Mcp-Param-*` from `x-mcp-header` schema annotations, mismatch → 400 with `-32020`; servers MUST validate `Origin` (403 on invalid) for DNS-rebinding defence, SHOULD bind to localhost when local, SHOULD authenticate; closing the SSE response stream is the cancellation signal; change notifications come via a long-lived `subscriptions/listen` POST; changes in this revision include "Removal of protocol-level sessions." and the GET stream; `Last-Event-ID` resumability is not supported; legacy GET/DELETE get 405; HTTP+SSE (2024-11-05) is deprecated. [VERIFIED — "Streamable HTTP", https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http, accessed 2026-09-02]
- Authorization (HTTP transports only; stdio SHOULD take credentials from the environment): based on OAuth 2.1 (draft-ietf-oauth-v2-1-13), RFC 6750, RFC 8414, RFC 7591, RFC 8707, RFC 9728, RFC 9207, Client ID Metadata Documents and OIDC Discovery; MCP servers MUST implement Protected Resource Metadata (RFC 9728) and clients MUST use it for AS discovery; AS MUST offer RFC 8414 or OIDC discovery and clients MUST support both; clients and AS SHOULD support CIMD, MAY support DCR (deprecated); clients MUST send the RFC 8707 `resource` parameter in authorization and token requests; tokens MUST be sent as `Authorization: Bearer` on every request and never in query strings; servers MUST validate audience, MUST only accept tokens issued for them, and "MCP servers MUST NOT accept or transit any other tokens."; 401/403/400 semantics and `WWW-Authenticate scope=` step-up flow are defined; clients MUST validate `iss` per RFC 9207 when present. [VERIFIED — "Authorization", https://modelcontextprotocol.io/specification/latest/basic/authorization, accessed 2026-09-02]
- Authorization security considerations: "MCP clients MUST implement PKCE" and MUST verify PKCE support via `code_challenge_methods_supported` (refuse if absent, including for OIDC providers), MUST use `S256` when capable; AS endpoints MUST be HTTPS; redirect URIs MUST be localhost or HTTPS and registered, validated by exact match; state parameters SHOULD be used; AS SHOULD issue short-lived tokens and MUST rotate refresh tokens for public clients; proxies with static client IDs MUST obtain per-client consent; MCP servers MUST NOT pass the client's token upstream; localhost redirect-URI risks require AS warnings. [VERIFIED — "Authorization Security Considerations", https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations, accessed 2026-09-02]
- Client registration: priority order is pre-registered credentials, then CIMD (if `client_id_metadata_document_supported`), then DCR (via `registration_endpoint`), then prompting the user; "Dynamic Client Registration is deprecated."; CIMD `client_id` MUST be an HTTPS URL with a path whose document lists at least `client_id`, `client_name`, `redirect_uris`; persisted credentials MUST be keyed by AS issuer and not reused across authorization servers. [VERIFIED — "Client Registration", https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration, accessed 2026-09-02]
- Security best practices: confused-deputy mitigation (per-client consent storage, consent UI, `__Host-` cookies, exact redirect-URI match, single-use `state`); "Token passthrough is explicitly forbidden"; SSRF defences for OAuth metadata fetches (HTTPS, block private/link-local ranges, validate redirects, egress proxies); state-handle hijacking (handles are not authentication; bind server-side to the verified user); local MCP server compromise (one-click configs MUST show the exact command and get explicit consent; sandbox spawned servers); OAuth URL validation (only http/https, never open via shell); stdio-proxy escalation; mix-up attacks; localhost redirect impersonation; CIMD trust policies; scope minimisation. [VERIFIED — "Security Best Practices", https://modelcontextprotocol.io/specification/latest/basic/security_best_practices, accessed 2026-09-02]
- Cancellation: client SHOULD send `notifications/cancelled` with `requestId` and optional `reason`; on Streamable HTTP closing the response stream is the signal and no notification is expected; on stdio the notification MUST be sent; receivers SHOULD stop processing, free resources and not respond; MAY ignore unknown/completed requests; both sides MUST tolerate races; implementations SHOULD set per-request timeouts (optionally reset by progress, but with a hard maximum); servers only send `notifications/cancelled` to tear down a `subscriptions/listen` stream. [VERIFIED — "Cancellation", https://modelcontextprotocol.io/specification/latest/basic/utilities/cancellation, accessed 2026-09-02]
- Progress: client opts in with `_meta.progressToken` (string or integer, unique across active requests); server MAY send `notifications/progress` with `progressToken`, monotonically increasing `progress`, optional `total` and `message`; notifications MUST stop after completion; both sides SHOULD rate-limit. [VERIFIED — "Progress", https://modelcontextprotocol.io/specification/latest/basic/utilities/progress, accessed 2026-09-02]

### Gmail API
- Scope table (classification as printed): `gmail.readonly` restricted; `gmail.compose` = "Manage drafts and send emails." restricted; `gmail.send` (send on your behalf) sensitive; `gmail.modify` (read/compose/send, no permanent delete) restricted; `gmail.insert` restricted; `gmail.labels` non-sensitive; `gmail.metadata` restricted; `gmail.settings.basic` and `gmail.settings.sharing` restricted; `https://mail.google.com/` (full incl. permanent delete) restricted; add-on scopes `gmail.addons.current.action.compose` non-sensitive, `...message.action` non-sensitive, `...message.metadata` and `...message.readonly` sensitive. Restricted scopes need restricted-scope OAuth verification and, if data is stored/transmitted, a security assessment. [VERIFIED — "Choose Gmail API scopes", https://developers.google.com/gmail/api/auth/scopes (served at https://developers.google.com/workspace/gmail/api/auth/scopes), accessed 2026-09-02]
- Draft-vs-send: drafts are created with `users.drafts.create` (RFC 2822 MIME, base64url in `message.raw`), updated with `users.drafts.update`, and sent with `users.drafts.send`; the Java sample uses the `GMAIL_COMPOSE` scope; a sent draft is deleted and replaced by a message labelled SENT. Creating a draft without sending therefore maps to `gmail.compose` (which also permits sending), while `gmail.send` only sends. [VERIFIED — "Create and send draft emails | Gmail | Google for Developers", https://developers.google.com/gmail/api/guides/drafts (served under /workspace/gmail/), accessed 2026-09-02]
